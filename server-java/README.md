# UptimeMonitor — Spring Boot backend

A full rewrite of `../server` (Node/Express/Sequelize) on **Java 21 + Spring Boot 4.1 +
Spring Data JPA + PostgreSQL**. It serves the same REST API and Socket.IO events, so the
React client works unchanged, and it uses the **same database schema**, so the Node server
remains a drop-in fallback against the same data.

## Quick start (local)

Prerequisites: JDK 21+, PostgreSQL, and Docker (only for running the tests).
Maven is not required — use the wrapper (`./mvnw`, or `mvnw.cmd` on Windows).

```bash
cd server-java
./mvnw spring-boot:run          # API on :5000, Socket.IO on :5001
```

Configuration is read from `../server/.env` automatically (same variable names as the Node
server). To override anything, copy `.env.example` to `server-java/.env`.

Then run the client against it:

```bash
cd client
npm run dev:java                # = vite --mode java (loads client/.env.java)
```

`npm run dev` still targets the Node server. Don't run both servers at once: they both
use port 5000 by default.

Health: `GET http://localhost:5000/api/health` (same body as Node) and
`/actuator/health`.

## Tests

```bash
./mvnw test                     # needs Docker running (Testcontainers starts postgres:17)
```

217 tests: JUnit 5 + Mockito + Spring Boot Test + Testcontainers. They include ports of all

## Database and migrations

Flyway owns the schema; `sequelize.sync({ alter: true })` is gone.

* `V1__baseline_schema.sql` is the exact schema Sequelize created (table and column names,
  enum types, defaults, indexes, FKs).
* On an **existing** Node database (no Flyway history), Flyway *baselines* at V1: V1 is
  skipped and only later migrations run. On first boot you'll see a new
  `flyway_schema_history` table.
* `V2` drops the numbered duplicate UNIQUE constraints (`Users_email_key1..N`) that
  `sync({ alter: true })` accumulated. The `afterMigrate` callback repeats this on every
  boot, because the Node server re-adds them whenever it runs.
* Hibernate validates the entities against the schema on startup (`ddl-auto: validate`).
* New schema changes: add `V3__description.sql`, and so on. Never edit an applied migration.

Switching back to Node needs no rollback: its `sync({ alter: true })` accepts the
Flyway-managed schema (verified end to end).

## Design decisions

**Socket.IO: netty-socketio, not native WebSocket/STOMP.** The client uses
`socket.io-client@4`, which speaks the Socket.IO protocol rather than raw WebSocket.
netty-socketio 2.x implements the v4 protocol, so:

* the client needs no source changes (verified with the client's own `socket.io-client`
  against the running jar);
* the client stays compatible with **both** backends. That matters while Node is the
  fallback: a STOMP rewrite would break real-time updates the moment you fall back.

The cost is that netty-socketio runs its own Netty listener on a second port
(`SOCKET_PORT`, default 5001). For local dev, `client/.env.java` sets
`VITE_SOCKET_URL=http://localhost:5001`. For deployment, you'll need either a reverse-proxy
rule (`/socket.io` → 5001) or, once Node is retired, a move to Spring WebSocket/STOMP on a
single port. The swap is contained: `RealtimeEvents` is the only seam, and the client
change is limited to `hooks/useSocket.js`.

**Wire compatibility with Node:**
* JWT: HS256 via jjwt, same secrets and claims (`userId`, `sid`, `jti`, `typ`).
* Passwords: BCrypt, byte-compatible with bcryptjs. This includes passwords over 72 bytes,
  which Spring's stock encoder rejects.
* MFA secrets: AES-256-GCM in the same `iv|tag|ciphertext` layout.
* Emails: validator.js `normalizeEmail()` ported exactly (e.g. Gmail dots removed).
* JSON: `Date#toISOString()` timestamps, nulls kept, Sequelize-style embedded associations
  (`"Monitor": {...}`).

**Security:**
* Spring Security runs a stateless JWT filter that re-checks the user, the session
  revocation and the password-change time on every request, like `auth.js`.
* RBAC uses method security (`@RequireAdmin`, `@RequireEditor` → `@PreAuthorize`), with
  Node's exact 403 messages.
* Rate limiting uses Bucket4j with the same windows, limits, messages and draft-7
  `RateLimit` headers.
* Helmet-equivalent headers, CORS, request IDs, env validation before startup.

**Runtime:**
* Virtual threads (Java 21) for requests, monitor checks and alert delivery.
* Checks run concurrently instead of one after another.
* Graceful shutdown (`server.shutdown=graceful`, 15s). The Socket.IO server stops first
  and the scheduler stops before the DataSource closes.

## Behavioural differences from the Node server

Response shapes are unchanged. These are deliberate fixes, each covered by a test:

* **Security**
  * An `mfaChallengeToken` can no longer be used as a Bearer access token. In Node it
    could, which bypassed the second factor.
  * `/api/team/members` no longer returns `mfaSecret` or `mfaBackupCodes`.
  * `/api/monitors/:id/checks` and `/incidents` no longer return another organization's
    data for a known UUID; they return an empty list.
  * Alert channel URLs pass through the SSRF guard (set `ALLOW_PRIVATE_URLS=true` locally
    for webhooks to localhost).
  * Unknown emails at login take the same time as known ones, so response timing no
    longer reveals which accounts exist.
* **Monitoring**
  * A 30-second monitor is checked every 30 seconds; in Node it was effectively every 60.
  * `responseTimeMs` excludes the separate TLS certificate probe.
  * Pausing a monitor while its check is in flight keeps it paused.
  * A new heartbeat monitor gets its grace period before the first ping; Node marked it
    down on the first tick.
  * A heartbeat ping to a paused monitor is recorded but doesn't un-pause it.
* **API**
  * `/api/auth/me` returns the organization as both `Organization` (as before) and
    `organization`. The dashboard reads the latter, so the status-page link now survives
    a page reload.
  * An empty public status page reports `operational`; Node reported `major_outage`.
  * Some invalid inputs now return 400 where Node returned a database 500: alert-channel
    updates, `/api/stats/monitors/<non-uuid>`, negative `?limit=`.
* **Validation**
  * When a field fails several rules, the `details` array lists one entry for it instead
    of one per failed rule.
* **Config**
  * JWT secrets must be at least 32 bytes in every environment, because HS256 requires it.
    Node only enforced this in production.

## Known limitations (same as Node unless noted)

* Joining a Socket.IO room is unauthenticated: the client sends no credentials. Payloads
  contain only status data.
* Rate-limit counters are in-memory and per instance.
* `email` alert channels are accepted but nothing is sent (there's no mailer).
* API keys can be created and revoked, but no route authenticates with them. Node's
  `apiKeyAuth` middleware was never mounted.
